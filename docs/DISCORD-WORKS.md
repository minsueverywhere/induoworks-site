# Discord 작품 파일 접수

2026-10-17 로컬 구현·검증 완료, 운영 등록·배포 전이다. 외부 링크 Work와는 별개로 Discord의 첨부 파일을 받아 호스트 승인 뒤 기존 정적 콘텐츠 저장소에 발행한다. 파일을 웹에 직접 업로드하거나 Discord CDN을 영구 파일 주소로 사용하지 않는다.

## 사용 흐름

1. 참여자는 Induo Works 서버에서 `/submit-work worker:frondward title:... description:... file:...`을 실행한다. 명령 설명은 승인 시 induo.works에 공개됨을 알린다. 제출자의 Discord ID는 기존 `studio_members` 또는 `studio_hosts`에서 확인한다. 계정 연결은 호스트가 먼저 등록한다.
2. 접수 결과는 본인에게만 보이는 Discord 응답이다. 승인 전에는 공개 콘텐츠 JSON·Works·마을이 바뀌지 않는다. 게시판 메시지를 자동 수집하거나 기존 대화를 스캔하지 않는다.
3. 호스트는 로컬 편집기의 **Discord 작품 접수 → 접수 불러오기 → 파일 미리보기**에서 검토한다. 음악은 실제 오디오 메타데이터로 재생 길이를 확인해야 한다. 음원을 자동재생하지 않는다.
4. **승인·콘텐츠 발행**은 파일 재검증, 이미지 미리보기/배지 생성, 현재 콘텐츠 검사, 자동 백업·충돌 검사, 저장, 콘텐츠만 배포, 공개 반영 확인을 수행한다. 저장하지 않은 다른 편집이 있으면 먼저 저장하거나 버려야 한다. 이미지 원본이나 음악은 감상 요청 전까지 씬이 불러오지 않는다.
5. 승인한 이미지는 `media`, 음악은 `tracks`에 `discord-접수ID`로 등록한다. Works·Workers·집 안 꾸미기 선택 항목이 같은 데이터를 사용한다. 제목은 우선 한국어·영어에 동일하게 넣고 이후 번역·설명을 편집할 수 있다. 그림의 설명도 보존한다. 기존 이미지 자동 전시 4개·프로젝트 9개 한도는 유지하며 초과 시 발행 전 검사가 거부한다.
6. **반려**는 공개 콘텐츠를 바꾸지 않고 임시 파일을 정리한다. 승인 후 실제 공개가 확인된 경우에도 임시 파일을 정리한다.

이미 존재하는 참여자 작성본은 승인본 변경으로 오래된 상태가 될 수 있다. 이 경우 기존 변경안의 내려받기·호스트 비교 절차를 유지한다. 새 파일 접수는 기존 작성본을 자동 덮어쓰거나 승인하지 않는다.

## 제한과 저장

- 파일 하나당 **8MiB**, 계정당 수신/검토/발행 중 **3건**, 전체 **100건·64MiB** 중 먼저 도달한 한도를 적용한다. Discord 계정 자체의 업로드 한도가 더 작으면 그 한도가 우선한다.
- 이미지: PNG/JPEG/WebP/AVIF/GIF. 음원: **MP3 또는 Opus OGG**. WAV·SVG·HTML·실행 파일과 확장자/실제 내용 불일치를 거부한다. 제출 메타데이터뿐 아니라 다운로드된 바이트 수·파일 시그니처·SHA-256을 검사한다. 호스트 단계에서는 이미지 디코딩(최대 4천만 픽셀)과 음악 메타데이터 재생 길이를 확인한다.
- 음악은 제출한 한 형식으로 등록할 수 있다. 존재하지 않는 대체 형식을 만들지 않는다. 두 형식이 등록되면 기기에 맞춰 선택한다. 구형 브라우저까지 지원해야 하면 호스트가 MP3 대체본을 추가한다.
- 승인 전에는 기존 비공개 D1에 파일을 512KiB 조각으로 임시 저장한다. Discord의 만료되는 첨부 주소와 interaction token은 DB에 저장하지 않는다. R2·새 유료 저장 서비스·봇 권한 확대는 필요하지 않다.
- 미승인 파일은 **7일** 후 접근·승인을 거부하며 다음 접수 또는 호스트 조회 때 회수한다. 별도 정기 삭제 작업은 없다. 처리된 기록은 30일 뒤 다음 접수에서 정리한다. 배포 결과가 불명확한 `publishing` 자료는 복구를 위해 만료로 삭제하지 않고 64MiB 한도에 계속 포함한다.
- 로컬 미리보기 캐시는 `.wrangler/intake-cache`에만 두고, 목록 조회 때 더 이상 대기하지 않는 캐시를 정리한다. 공개 정적 배포는 승인본이 참조하는 파일만 포함한다. 최종 정적 호스팅의 파일별 25MiB 제한도 기존 검사로 유지한다.

## 코드 연결과 신뢰 경계

- 기존 커뮤니티 봇의 서명 검증 후 `submit-work`만 고정 사이트 주소 `/api/discord-work`로 전달한다. 원본 본문·Discord 서명을 보존하며 Bot Token을 전달하지 않는다. 피드백 버튼·Durable Object·기존 명령은 유지한다. 봇 변경의 원본은 Induo Works workspace의 `social-media/discord/feedback-bot`이다.
- 사이트도 Ed25519 서명·5분 타임스탬프·앱/서버/명령·현재 업체 권한을 검증한다. 알려진 Discord 첨부 CDN의 HTTPS 주소만 받고 리다이렉트는 따라가지 않는다. 본문 32KiB, 계정 단위 요청 제한, 중복 interaction ID와 원자적 용량 예약을 사용한다.
- 응답을 지연 승인한 뒤 Worker `waitUntil`에서 파일을 보관한다. 봇은 2.2초 내 사이트 응답이 확정되지 않으면 결과를 단정하지 않고 호스트에게 확인하도록 안내한다. 접수·승인 모두 불명확한 결과를 자동 재시도하지 않는다.
- 호스트 검토는 기존 loopback·Host·동일 출처·실행 토큰 보호를 사용한다. Cloudflare에 로그인한 로컬 Wrangler가 D1을 조회하므로 브라우저나 참여자에게 배포 키·DB 권한을 주지 않는다. 미리보기 GET도 같은 출처의 편집기에서만 허용한다.
- 승인 시 제출자의 현재 업체 권한을 다시 확인하고 공개 직전 파일 해시·형식·콘텐츠 참조·점유 영역·저장본 버전을 검사한다. 사전에 확정한 상태를 `publishing`으로 예약한 뒤 저장/배포한다.

## 운영 반영 순서

1. 사이트 전체 검사·빌드 후 `wrangler d1 migrations apply STUDIO_DB --remote --config wrangler.jsonc`로 `0003_discord_intake.sql`을 적용한다. 기존 계정·작성본·요청 테이블은 바꾸지 않는다.
2. 사이트 코드를 배포한다. 공개 설정 `DISCORD_CLIENT_ID`, `DISCORD_GUILD_ID`, `DISCORD_PUBLIC_KEY`는 `wrangler.jsonc`를 따른다. 새 비밀 키는 필요 없다. 기존 OAuth Client Secret이나 Bot Token을 재발급하지 않는다.
3. 커뮤니티 봇의 변경을 테스트·dry-run 후 배포한다. 기존 Discord Interactions Endpoint 주소와 Durable Object namespace는 바꾸지 않는다.
4. `scripts/discord-command.mjs`의 `workCommand`를 기존 앱·길드에 **개별 생성/갱신**한다. 전체 명령 덮어쓰기를 사용하지 않는다. 기본 공개 언어는 영어다.
5. 작은 테스트 파일을 실제 계정으로 제출해 본인 전용 대기 응답·호스트 미리보기·반려까지 확인한다. 실제 파일 공개 검증은 별도로 승인한 자료만 사용한다. 새 단일 형식 음악을 발행하기 전에 새 사이트 코드가 배포되어 있어야 한다.

## 실패 후 복구

저장 전 검사 실패는 접수를 대기로 남긴다. 저장에 실패하면 발행 예약을 해제한다. 저장 후 배포/확인이 실패하면 로컬 승인본과 `publishing` 상태를 보존한다. 호스트는 **다시 불러오기 → 저장본과 배포 결과 확인 → 필요 시 기존 콘텐츠만 배포 → 발행 확인**으로 이어간다. 발행 확인은 공개 JSON의 ID·소속·해시를 포함한 파일 경로가 실제 접수와 일치할 때만 완료하며 임시 파일을 정리한다. 같은 접수를 다시 승인하거나 DB 예약을 지워 재제출하지 않는다.

## 검증 상태

테스트는 실제 SQLite SQL, 서명·재전송·권한, 위장 파일/용량/주소 거부, 계정·전체 한도·동시 접수, 조각 재조립·만료, 호스트 승인/반려, 백업/충돌·불명확한 배포 보존, 단일 MP3의 Works·지연 재생을 포함한다. 격리된 Chrome 화면에서 접수 목록·이미지 미리보기·반려를 확인했다. 격리 서버는 공개 배포를 실행할 수 없고 검증 후 종료했다. 운영 명령 실행·D1 실제 업로드·공개 발행은 아직 검증하지 않았다.
